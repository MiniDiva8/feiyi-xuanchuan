# 三人加入协作：GitHub + Codex Cloud 原生流程

仓库：https://github.com/MiniDiva8/feiyi-xuanchuan （私有）
以 GitHub 的 main、Issues、PR 和检查结果为共同状态；每个人使用自己的账号和独立 Cloud 工作区。

## 1. 接受邀请
donghaochen45-pixel、zhupaifan 分别登录自己的 GitHub，在通知中接受 MiniDiva8 的仓库邀请。
然后亲自打开仓库，确认能看到代码、Issues 和 Pull requests。邀请已发出不等于已接受。

## 2. 每人连接自己的 Cloud 环境
在各自 Windows Codex App 登录各自 Codex/ChatGPT 账号：
1. 新任务选择“云端 / Cloud”→“选择环境”→“创建环境”。
2. 连接自己的 GitHub，选择 MiniDiva8/feiyi-xuanchuan，默认分支 main。
3. 搜索时先输入仓库名 feiyi-xuanchuan。仍不显示时，点击“配置访问权限”；由本人/仓库所有者在 GitHub 官方页面给应用添加此仓库访问，保存后重新打开列表。
4. 点击“开始设置 / Get started”，让 Codex 准备环境，检查实际报告，再点“发布 / Publish”。
5. 看到环境已发布后，选择它开始新任务。三人分别完成；环境可见范围选 Only me。

初始仓库是协作基础配置，运行时为 Python 3.11+、Git 2.38+。后续业务框架与依赖在开发中按需确定。
Cloud 的实际权限/可用性以每个人账号界面为准，不能用别人的环境代替本人验证。

## 3. 用 Issue 分任务
| 开发者 | 建议负责范围 |
|---|---|
| MiniDiva8 | 前端 apps/web/ |
| donghaochen45-pixel | 后端 services/api/ |
| zhupaifan | AI services/marketing-ai/ |

在 GitHub 新建 Issue，写清结果、允许路径和验收方法，只设置一名 Assignee。
共享接口、根配置先在 Issue 协商；分工可经团队确认后调整。

## 4. 把任务交给自己的 Codex
在本人已发布的 Cloud 环境中粘贴，替换用户名和编号：

> 使用我的 GitHub 账号【用户名】完成 Issue #【编号】。
> 先读 AGENTS.md 和 Issue，核实唯一负责人是我，拉取/刷新最新 main 并记录提交 SHA。
> 从该基线创建 codex/【用户名】/issue-【编号】-【英文短名】，只修改已分配范围。
> 优先使用 GitHub 和 Cloud 原生提交、推送及 Create PR 能力，已有脚本只是可选工具。
> 完成实际测试后创建草稿 PR，正文写 Closes #【编号】及测试证据；不能执行的步骤明确标记。
> 不合并、不公开仓库、不购买服务、不修改其他人的模块。

若该环境没有可用的提交/推送/Create PR 权限，先修复本人的 GitHub 连接；不能把“生成了 diff”写成“PR 已创建”。

## 5. 评审后由人合并
作者准备好后，将 Draft 改为 Ready for review。
另一名成员检查 Files changed、当前 head 的测试与 Actions，再提交 Approve；共享配置改动由另外两人审查。
确认当前 PR 的 collab-quality 通过且 GitHub 无冲突后，由人选择 Squash and merge。
当前账号的私有分支强制保护申请返回 403，尚未启用；不要把团队约定当成服务器已强制执行。

## 6. 新任务重新读 main
合并后，每个人在新任务中再次拉取/刷新 main，记录 SHA，确认包含队友的变化，再开新的独立分支。
已有 Cloud 任务保留自己的状态，不会实时共享队友的未提交文件。

本次 GitHub 验收 PR 保持未合并。两位成员接受邀请、三个个人 Cloud 环境发布，以及三人真实 Cloud 协作仍需本人逐项确认。
